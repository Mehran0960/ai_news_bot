# توسعهٔ پیام‌رسان‌های OfferChin

## سیاست هزینه و معماری

این توسعه از همان GitHub Actions و صف انتشار فعلی استفاده می‌کند. هیچ VPS، Make.com،
سرویس یکپارچه‌ساز پولی یا کتابخانهٔ وابسته به SaaS اضافه نشده است. خطای هر مقصد، تلگرام و بله را متوقف نمی‌کند.

رایگان‌بودن زیرساخت با رایگان‌بودن API پلتفرم یکی نیست. در مورد روبیکا، مسیر Bot API
مستقیم و مستند است و در این طراحی سرویس واسطه‌ای خریداری نمی‌شود؛ سقف‌ها یا شرایط مصرف
خود روبیکا باید از حساب سازندهٔ بات بررسی شود.

برای ایتا، مستند عمومی رسمیِ بررسی‌شده دربارهٔ ۵۰هزار اعتبار رایگان مربوط به
/api/app/sendMessage برای ارسال برنامه به کاربرانی است که اجازهٔ دریافت پیام داده‌اند.
این اعتبار، اثبات رایگان‌بودن ارسال فایل به کانال با Bot API نیست. به همین دلیل آداپتور
EitaaYar آزمایشی است و به‌صورت پیش‌فرض خاموش می‌ماند. پیش از استفادهٔ مستمر، تعرفه و
مجازبودن انتشار کانالی باید در پنل ایتایار تأیید شود.

سروش‌پلاس فعلاً متصل نشده است؛ مسیرهای یکپارچه‌ساز شناخته‌شده وابستگی بیرونی و احتمال
تعرفه ایجاد می‌کنند و مسیر رسمی رایگان برای انتشار خودکار کانال هنوز تأیید نشده است.

## تنظیم روبیکا

۱. از مسیر رسمی روبیکا یک بات بسازید.
۲. بات را به کانال OfferChin اضافه و مجوز ارسال پیام/فایل را به آن بدهید.
۳. شناسهٔ کانال مقصد را از مسیرهای مجاز روبیکا دریافت کنید.
۴. فقط Secret با نام RUBIKA_BOT_TOKEN لازم است؛ شناسهٔ کانال عمومی است و پس از
استخراج موفق، در workflow ناشر ثبت شده است:

- RUBIKA_CHANNEL_ID = c0EH9WW0c7fa831d965d050233b7ab35

در صورت تغییر کانال می‌توان مقدار جایگزین را به‌صورت Actions Variable با همین نام
RUBIKA_CHANNEL_ID تعریف کرد؛ مقدار Variable بر مقدار پیش‌فرض workflow اولویت دارد.

۵. در بخش Variables همین صفحه مقدار RUBIKA_ENABLE_PUBLISHING را true کنید تا انتشار
روبیکا فعال شود. این Variable فعلاً false/تعریف‌نشده است؛ بنابراین با وجود تکمیل
شناسه و توکن، هیچ محصولی تا فعال‌سازی صریح به روبیکا ارسال نمی‌شود.

## تنظیم ایتا

۱. از ایتایار بات بسازید و دسترسی انتشار آن را در کانال مقصد مجاز کنید.
۲. این GitHub Actions Secrets را اضافه کنید:

- EITAA_BOT_TOKEN
- EITAA_CHANNEL_ID

۳. فقط پس از اطمینان از تعرفه، اعتبار و یک تست دستی کنترل‌شده، Variable
EITAA_ENABLE_PUBLISHING را true کنید. پیش‌فرض آن false است.

اگر ساختار پاسخ سرویس شناسهٔ پیام ندهد، سیستم فقط رسید پذیرش API را ذخیره می‌کند؛
شناسهٔ ساختگی تولید نمی‌کند.

## وضعیت انتشار

- sent یعنی API مقصد درخواست انتشار را پذیرفته/شناسه پیام برگردانده است؛ این وضعیت به‌تنهایی
تأیید مستقل مشاهدهٔ عمومی پست نیست.
- platform_message_ids فقط شناسه‌های واقعی برگشتی را نگه می‌دارد.
- platform_delivery_receipts رسیدهایی را نگه می‌دارد که API قبول کرده ولی شناسهٔ پیام نداده است.
- failed با زمان تلاش بعدی و backoff ثبت می‌شود.
- not_connected یعنی Secret/Variable لازم وجود ندارد یا آداپتور عمداً خاموش است.

## محدودیت‌های فعلی

- آداپتورهای جدید فقط پست تصویریِ محصول منتخب را ارسال می‌کنند؛ چرخهٔ ویدئو برای روبیکا و
ایتا در این مرحله اضافه نشده است.
- مقصدهای جدید فقط برای آیتم‌های صف جدید فعال خواهند بود و انتشار عمومی آیتم‌های قدیمی
به‌صورت خودکار به عقب برگردانده نمی‌شود.
- اجرای زنده پس از افزودن Secret/Variableها باید ابتدا با یک پست آزمایشیِ مورد تأیید مالک
کانال انجام شود.


## کشف شناسه کانال روبیکا

پس از ثبت Secret با نام RUBIKA_BOT_TOKEN و ادمین‌کردن بات در کانال، گردش‌کار
Rubika Channel ID Discovery از getUpdates رویدادهای دریافتی را می‌خواند و با getChat
username دقیق را همراه با نوع چت تطبیق می‌دهد؛ عنوان مشابه به‌تنهایی پذیرفته نمی‌شود. این گردش‌کار هیچ پیامی ارسال، ویرایش یا حذف نمی‌کند
و متن پیام‌ها را در log چاپ نمی‌کند. شناسه واقعی با الگوی RUBIKA_CHANNEL_ID_FOUND در
خروجی ثبت می‌شود.

برای پیام‌های عادی کانال باید گزینه «دریافت همه پیام‌های کانال و گروه» در BotFather
فعال باشد؛ پس از فعال‌سازی، یک پیام متنی تازه در کانال بفرستید. اگر این دسترسی خاموش
باشد، ممکن است فقط پیام‌های منشن‌شده یا دستوری به بات برسند.


## نتیجهٔ کشف کانال OfferChin — ۷ نوامبر ۲۰۲۶

API روبیکا کانال را با username برابر offerchin، عنوان «آفِرچین» و نوع Channel تأیید کرد.
شناسهٔ chat_id برابر c0EH9WW0c7fa831d965d050233b7ab35 است. این شناسه رشته‌ای حروفی‌ـ‌عددی
است و به‌عنوان مقدار پیش‌فرض غیرمحرمانه در workflow ناشر ثبت می‌شود. توکن همچنان فقط
در GitHub Actions Secret با نام RUBIKA_BOT_TOKEN نگهداری می‌شود. انتشار روبیکا تا فعال‌سازی
صریح RUBIKA_ENABLE_PUBLISHING خاموش می‌ماند.


## یکسان‌سازی کپشن روبیکا و لینک عضویت — ۷ نوامبر ۲۰۲۶

- کپشن روبیکا از همان تابع `build_caption` مشترک Telegram/Bale ساخته می‌شود تا عنوان، ترتیب متن، قیمت فعلی، درصد تخفیف، عبارت خرید اقساطی و جداکننده‌ها یکسان بمانند.
- مقصد لینک عضویت کانال در تنظیمات کپشن، `https://rubika.ir/offerchin` است.
- API رسمی روبیکا در `sendFile` پارامتر `inline_keypad` را می‌پذیرد؛ برای لینک‌دار بودن عبارت عضویت، دکمهٔ نوع Link با مقصد مستقیم کانال در همان پیام تصویری درج می‌شود.
- دکمهٔ مستقل خرید افیلیت نیز در همان inline keypad حفظ شده است. به این ترتیب یک پست تصویر با دو دکمهٔ زیر آن ارسال می‌شود: «مشاهده و خرید» و «عضویت در کانال آفِرچین».
- کپشن در فیلد text روبیکا به متن ساده تبدیل می‌شود؛ نشانه‌های قالب‌بندی Markdown/HTML به شکل خام به مخاطب نمایش داده نمی‌شوند. CTA عضویت در قالب دکمهٔ کلیکی زیر همان پیام ارائه می‌شود، نه یک پیام دوم.
- تست آداپتور باید متن مشترک کپشن، URL دقیق خرید، URL دقیق کانال، ترتیب دکمه‌ها و نبود پیام اضافی را بررسی کند.


## استاندارد مشترک کپشن و CTA — ۷ نوامبر ۲۰۲۶

متن‌های قابل‌مشاهدهٔ کپشن و اقدام‌ها از فایل `offerchin_copy.py` می‌آیند؛ این فایل منبع واحد عبارت‌های فروش ویژه، عنوان محصول، قیمت فعلی، تخفیف، دیجی‌پی، جداکننده، دکمهٔ خرید و عضویت است. تغییر یک عبارت باید در همین منبع انجام شود، نه به‌صورت کپی‌های جداگانه در هر آداپتور.

- متن خرید در همهٔ مقصدها با الگوی واحد «🛍️ مشاهده و خرید از {نام فروشگاه}» ساخته می‌شود. تلگرام، بله و روبیکا آن را روی دکمهٔ متصل به لینک افیلیت معتبر می‌گذارند؛ ایتا فعلاً همان عبارت را در کپشن و بلافاصله پیش از URL معتبر می‌آورد.
- متن عضویت یکسان است: «➕ عضویت در کانال آفِرچین». در تلگرام و بله لینک درون کپشن، و در روبیکا دکمهٔ لینک‌دار در همان پیام تصویر قرار می‌گیرد.
- در ایتا، چون برای آداپتور فعلی EitaaYar قرارداد دکمهٔ لینک‌دار روی sendFile به‌طور قابل‌اتکا تأیید نشده، دکمهٔ ساختگی ارسال نمی‌شود. تا زمانی که URL عمومی کانال در Actions Variable با نام `EITAA_CHANNEL_URL` تعریف نشده، CTA عضویت حذف می‌شود؛ هیچ آدرس حدسی به متن اضافه نمی‌شود. با تعریف URL معتبر HTTPS، متن عضویت به همراه همان URL در کپشن درج می‌شود تا کلاینت ایتا آن را به‌عنوان پیوند تشخیص دهد.
- تفاوت HTML، Markdown و متن ساده صرفاً محدودیت قالب‌بندی هر API است؛ عبارت‌ها، ترتیب محتوای تجاری و متن اقدام‌ها از یک استاندارد مشترک می‌آیند.
- تست‌های آداپتور باید ثابت کنند که متن خرید/عضویت در Rubika و Eitaa با منبع مشترک برابر است، لینک محصول به URL تأییدشده متصل می‌ماند و لینک عضویت ایتا بدون تنظیم URL ساخته نمی‌شود.



## اصلاح قالب روبیکا و یکسان‌سازی CTA — ۸ نوامبر ۲۰۲۶

در بازبینی اجرای قبلی مشخص شد که دعوت عضویت روبیکا فقط به‌صورت دکمهٔ دومِ کی‌پد دیده می‌شد و داخل متن کپشن لینک متنی نداشت؛ بنابراین از نظر محل و قالب CTA دقیقاً با تلگرام و بله یکسان نبود. این رفتار اصلاح شد.

- کپشن روبیکا همچنان از همان `build_caption` مشترک Telegram/Bale ساخته می‌شود؛ متن، ترتیب قیمت و تخفیف، عبارت دیجی‌پی، جداکننده و عبارت عضویت یکسان می‌ماند.
- عبارت «➕ عضویت در کانال آفِرچین» در خود متن کپشن به‌صورت پیوند واقعی Rubika `metadata` از نوع `Link` به `https://rubika.ir/offerchin` متصل می‌شود. محدودهٔ متن با واحد UTF-16 محاسبه می‌شود تا offset پیوند با متن نهایی و ایموجی‌ها دقیق باشد.
- کی‌پد عادیِ زیر همان پست فقط یک دکمهٔ خرید دارد که به لینک افیلیت تأییدشده متصل است؛ مانند دکمهٔ خرید تلگرام و بله. دعوت عضویت دیگر به‌عنوان دکمهٔ دومِ عادی تکرار نمی‌شود.
- اگر Rubika با پاسخ صریح `INVALID_INPUT` قالب metadata را رد کند، مسیر fallback همان پست را با دو دکمهٔ مستقل Link (خرید و عضویت) ارسال می‌کند. خطای شبکه یا نتیجهٔ مبهم هرگز retry نمی‌شود تا پست تکراری ساخته نشود.
- این پیاده‌سازی در تست آداپتور، محدودهٔ UTF-16، لینک دقیق عضویت، لینک دقیق خرید و مسیر fallback را کنترل می‌کند. موفقیت تست API جایگزین مشاهدهٔ یک پست عمومی زنده نیست؛ انتشار روبیکا همچنان به Variable صریح `RUBIKA_ENABLE_PUBLISHING=true` وابسته است.

## قاعدهٔ اجباری نوشتار نام برند — ۸ نوامبر ۲۰۲۶

- در هر متن نمایشی، عنوان کپشن، عنوان/توضیح ویدئو، متن تصویر یا پیام تبلیغاتی، نام لاتین برند فقط به شکل دقیق `OfferChin` نوشته می‌شود؛ `Offerchin`، `offerchin` و `OFFERCHIN` برای نام نمایشی مجاز نیستند.
- نرمال‌ساز مشترک `normalize_brand_display_name` پیش از ساخت کپشن، ویدئو و metadata آپارات/فیلو این قاعده را اعمال می‌کند.
- این قاعده روی شناسهٔ واقعی، URL، username، نام فایل/ماژول، متغیر محیطی یا API ID اعمال نمی‌شود. برای نمونه `rubika.ir/offerchin` و `youtube.com/@offerchin` باید دقیقاً به همان صورت معتبر باقی بمانند.
